Лабораторная работа: Разработка и интеграция модулей проекта (командная работа)
Цель работы: получить практический опыт декомпозиции сложной задачи на независимые модули, разработки по контракту (contract-first), организации командной работы в условиях ограниченного времени и интеграции результатов с использованием системы контроля версий.
Задачи:
1.	Провести анализ требований к системе и выполнить архитектурную декомпозицию.
2.	Сформировать API-контракты для взаимодействия модулей.
3.	Распределить роли в команде и параллельно разработать два независимых модуля.
4.	Выполнить слияние кода и интеграционное тестирование.
5.	Подготовить краткий отчет о конфликтах при слиянии и принятых решениях.
Предварительная подготовка (до начала занятия): Студенты должны иметь:
•	Установленный Git, редактор кода или IDE.
•	Базовые навыки работы с терминалом.
•	Созданный репозиторий на GitHub / GitLab / Bitbucket. Важно: ветка main/master защищена от прямого пуша (через настройки CI/CD или правила защиты ветки). Все изменения вносятся только через пул-реквесты (Pull Requests) и проходят код-ревью сокомандниками.
•	Знакомство с инструментами автоматизированного тестирования (например, Postman, Pytest, JUnit).
Исходные данные (легенда проекта): Заказчику требуется прототип сервиса «Умный планировщик задач». Система должна состоять из двух микросервисов:
1.	Task Service — отвечает за создание, редактирование, удаление и получение списка задач.
2.	Notification Service — подписывается на события создания новых задач и отправляет уведомления пользователю (в рамках лабораторной работы эмулирует отправку записью в лог-файл или консоль).
Взаимодействие между сервисами происходит асинхронно через общую шину событий (Message Broker). Для упрощения в рамках лабработы используется паттерн «HTTP-вебхук» (один сервис вызывает эндпоинт другого).
Задание:
Этап 1. Подготовка и распределение ролей (10 минут) Команда состоит из 3–4 человек. Участники распределяют следующие роли:
•	Архитектор / Tech Lead (1 чел.): отвечает за финальную сборку, разрешение конфликтов слияния, проверку соответствия контрактов. Не пишет бизнес-логику модулей, но может писать интеграционные тесты.
•	Backend-разработчик Task Service (1–2 чел.): реализует логику управления задачами.
•	Backend-разработчик Notification Service (1 чел.): реализует логику обработки уведомлений.
Этап 2. Проектирование контракта (15 минут) Вся команда совместно проектирует единый документ спецификации (допускается использование простого Markdown-файла API_CONTRACT.md в корне репозитория):
1.	Схема данных Task: id (UUID), title (string), description (string), status (enum: new, in_progress, done), created_at (ISO8601).
2.	Endpoint 1 (Task Service): POST /api/tasks. Принимает JSON тела задачи (без id и created_at). Возвращает созданную задачу со всеми полями и кодом 201.
3.	Endpoint 2 (Notification Service): POST /api/webhooks/task_created. Принимает JSON объекта Task. Возвращает 200 OK.
4.	Формат сообщения вебхука: Определить точное тело запроса, которое Task Service будет отправлять в Notification Service после успешного создания задачи.
Разработчики создают свои рабочие ветки (feature/tasks-service, feature/notifications-service) от общей ветки dev.
Этап 3. Параллельная разработка (45 минут) Команды работают изолированно над своими модулями. 
Для разработчиков модулей:
•	Реализовать серверную часть согласно контракту.
•	Обязательное покрытие основного сценария юнит-тестом или простым сценарным тестом.
•	Внедрить обработку ошибок: если принимающий сервис недоступен или возвращает ошибку, ваш модуль не должен падать (реализовать повторную попытку отправить событие через очередь сообщений в памяти или просто залогировать неудачу).
•	Задокументировать локальные точки отказа.
•	Сделать коммиты с осмысленными сообщениями и запушить ветку в удаленный репозиторий.
Рекомендации по стеку: Студенты могут использовать любой знакомый им язык. Оптимально выбрать легковесные инструменты:
•	Python + FastAPI (позволяет автоматически генерировать документацию и быстро поднять сервер).
•	Node.js + Express.
•	Java/Kotlin + Spring Boot Initializr (если курс ориентирован на энтерпрайз).
Этап 4. Интеграция и разрешение конфликтов (30 минут)
1.	Разработчики открывают Pull Request'ы в ветку dev. Архитектор выступает в роли ревьюера: проверяет соответствие кода подписанному контракту, оставляет комментарии, запрашивает исправления.
2.	После одобрения первого PR выполняется мерж в dev.
3.	Второй разработчик обновляет свою ветку (git pull origin dev) и сталкивается с конфликтом (конфликт в файле контракта API_CONTRACT.md или в структуре общих типов данных). 
4.	Команда должна вручную разрешить конфликт, согласовав итоговую версию контракта. Использование команды git rebase приветствуется для сохранения линейной истории.
5.	Выполнить запуск обоих сервисов. 
6.	Провести ручное сквозное (end-to-end) тестирование: отправить запрос на POST /api/tasks инструмента Postman/curl. Убедиться, что Task Service корректно сохранил задачу и успешно вызвал вебхук, а Notification Service получил данные и зафиксировал уведомление.
7.	Создать Pull Request из ветки dev в защищенную ветку main и смержить его.
